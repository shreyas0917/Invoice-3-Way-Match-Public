# ADR 0009 - SAP BTP deployment

- Status: accepted (prepared and built locally; **not deployed** - no BTP account was available)
- Date: 2026-11-03
- Phase: 11

## Context

Phases 0-10 run locally. Phase 11 prepares the same single CAP application (no microservices) for
SAP BTP, Cloud Foundry: SAP HANA Cloud, XSUAA, App Router, Destination service, MTA deployment.
Neither the Cloud Foundry CLI, the BTP CLI nor a BTP login were available while this was built, so
everything below is verified **locally** only (tests, CAP production build, `mbt build`, the
built App Router and the production profile started with fake bindings).

## Decisions

1. **Generated by CAP, then reviewed.** `cds add hana,xsuaa,approuter,destination,mta`
   (cds-dk 10.2.0) produced `mta.yaml` (project root), `xs-security.json`, `.deploy/app-router`,
   `db/undeploy.json` and the dependencies `@cap-js/hana`, `@sap/xssec`. The App Router stays
   where CAP puts it (`.deploy/app-router`, not the blueprint's `deployment/approuter`) so that
   later `cds add` runs keep working; `mta.yaml` stays at the root (blueprint: "fine").

2. **Architecture.**

   ```
   Browser -> App Router (XSUAA login, serves the 5 Fiori apps) --/odata, JWT--> CAP service
                                                                                 |- HANA Cloud (HDI container)
                                                                                 |- Destination service -> S/4HANA APIs
   ```
   Modules: `invoice-workbench` (App Router, 256 MB), `invoice-workbench-srv` (CAP, 256 MB),
   `invoice-workbench-db-deployer` (HDI). Resources: XSUAA `application`, HANA `hdi-shared`,
   Destination `lite`.

3. **The App Router serves the UI.** CAP's production build contains no `app/` files, so
   `scripts/build-approuter-ui.js` (run by `mta.yaml`) copies `app/index.html` and the five
   `webapp` folders into `.deploy/app-router/resources` (git-ignored). Routes (`xs-app.json`):
   `/odata/...` -> CAP (`srv-api`, token forwarded, CSRF protection), everything else ->
   `resources`; every route requires XSUAA. Nothing else of the CAP service is routed. The
   generated `default-env.json` (local only) is excluded from the archive.

4. **Authorization unchanged; XSUAA maps onto it.** Scopes and role templates `APClerk`,
   `Buyer`, `APManager` = the roles in `@requires`/`@restrict` (a test compares them with the
   model). `purchasingGroup` is a **required** attribute on the Buyer template only (the
   generated generic "userattributes" template was removed). XSUAA delivers it as an array;
   CAP turns `purchasingGroup = $user.purchasingGroup` into an OR over the values, and a missing
   or empty value matches nothing - tested with XSUAA-shaped users. `mta.yaml` declares the role
   collections `AP_Clerk` and `AP_Manager`; Buyer collections need a purchasing-group value, so an
   administrator creates them (`AP_Buyer_001`, ...). No CDS annotation changed.

5. **Persistence: SAP HANA Cloud** via `@cap-js/hana` (production profile); SQLite stays for
   development and tests. Only `db/data` is deployed: code lists, currencies, the default
   tolerance rules and approval policies (configuration, editable in the apps). No invoices,
   no `test/data`, no MOCK S/4 data (`s4mock`, `s4api`) - verified in the build output.

6. **S/4 connectivity through destinations.** Production: the Phase 10 adapter, each SAP API
   with `credentials.destination` (`S4HANA_PURCHASEORDER_2`, `S4HANA_MATERIAL_DOCUMENT`,
   `S4HANA_BUSINESS_PARTNER`) and `requestTimeout: 5000`. One destination per API, so the full
   service root URL and authentication live in the Destination service, not in Git or code.
   CAP resolves destination names with the SAP Cloud SDK (`@sap-cloud-sdk/http-client`,
   `connectivity`, `resilience`, now dependencies).

7. **Production hardening of Phase 10 limitations.**
   - *Raw SAP errors in the console:* CAP's `remote` logger writes them at warn level; the
     production profile sets it to `error`. The facade guard now writes its own console warning
     per failed call - sanitized like MessageLog, with the correlation ID.
   - *Permanent data refusals* (unsupported movement type, price per another unit) answer
     **502 S4_DATA_UNSUPPORTED** ("Retrying will not help ...") instead of 503 "try again".
     Phase 10 adapter tests now expect that code (stricter, not weaker).
   - *Timeout:* `requestTimeout: 5000` makes CAP abort the HTTP request itself (AbortSignal in
     the fetch client, the Cloud SDK's timeout middleware), matching the guard's 5 s limit.
   - *Mocks in production:* impossible - no mock implementation, no mock data model, and the
     adapter refuses to start without credentials (Phase 10).

8. **Launch page.** The mocked-user hints are shown only on localhost; on BTP the page says
   sign-in is through XSUAA. Its stale "logging comes in phase 8" text was corrected.

## Sandbox versus real S/4HANA

The blueprint suggests destinations to the SAP Business Accelerator Hub **sandbox** (API key
header). The sandbox is SAP's read-only demo system with SAP's demo data - not a transactional
S/4HANA, and its products/API versions may differ from the on-premise S/4HANA definitions
imported in phase 10. A sandbox destination proves connectivity and mapping against SAP-hosted
data only; it must be labelled as such. Unsupported data (e.g. other movement types) is refused
explicitly (502), so mismatches surface instead of producing wrong quantities.

## Consequences and limitations

- **Not deployed.** No `cf deploy` was run; no real XSUAA login, HANA persistence or S/4
  connectivity has been verified. The blueprint's done criterion (deployed app passes the demo
  script with real login, recording saved) is open.
- HDI artefacts were generated and the archive built, but not validated against a HANA
  instance (needs the HDI deployer and a database).
- HANA Cloud free tier stops nightly and must be restarted; trial accounts expire.
- `.deploy/app-router` holds no secrets; credentials only via service bindings and destinations.
- On-premise S/4HANA would additionally need the Connectivity service and SAP Cloud Connector
  (`ProxyType: OnPremise`); not configured.
